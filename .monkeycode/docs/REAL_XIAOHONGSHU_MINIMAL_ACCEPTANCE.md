# 真实小红书最小发布验收协作说明

## 目标

在不扩大范围的前提下，完成一次“真实小红书最小发布验收”，验证当前系统是否已经具备把一条已确认内容交给 OpenClaw 执行，并获得真实成功结果或真实失败结果的能力。

本轮目标不是“全面支持真实小红书自动化”，而是完成最小可证明闭环。

## 本轮验收范围

只验收以下最小路径：

1. 选择 1 个真实小红书账号
2. 选择 1 条已经 `approved` 的内容
3. 通过系统触发“交给 OpenClaw 执行”
4. 验证真实执行结果：
   - 成功发布
   - 或可解释失败
5. 验证前端页面是否正确承接真实结果

## 本轮不做

1. 不做多账号并行发布验收
2. 不做批量任务验收
3. 不做复杂排期
4. 不要求一次性找齐所有小红书网页接口
5. 不要求真实数据回收本轮同时闭环

## 成功标准

满足以下任一条件即可视为本轮验收通过：

1. 至少 1 条内容通过真实小红书账号完成真实发布，并得到可核验成功结果
2. 至少 1 条内容触发真实平台失败，并拿到可解释失败结果，且前后端页面承接正确

## 前置条件

### 账号与环境

1. 已准备 1 个可用的真实小红书账号
2. 该账号的登录态可由 OpenClaw 执行环境使用
3. 验收时优先选用单图文、低风险内容，避免复杂内容格式

### 系统前置状态

1. QQ / OpenClaw 入站链路已完成
2. 账号归属真实化已完成
3. 真实生成链路已完成
4. 系统内部发布闭环已完成：
   - `approved -> publishing -> published / publish_failed`
5. 前端已完成 `/review`、`/dashboard`、`/posts/[id]` 的真实发布状态承接

## 后端职责

### 1. 真实发布执行接入

1. 在现有发布适配层边界内接入真实小红书发布执行实现
2. 不要把业务层写死在具体页面细节中
3. 继续沿用现有状态流转：
   - `approved -> publishing`
   - `publishing -> published`
   - `publishing -> publish_failed`

### 2. 真实结果回写

后端至少要稳定回写以下信息：

1. 当前发布状态
2. 发布时间
3. 平台帖子标识或等价成功标识
4. 失败原因
5. 失败分类：
   - `retryable`
   - `non_retryable`
   - `rate_limited`
6. 发布记录时间线

### 3. 验收期日志与排障信息

1. 保留最小执行日志，便于区分：
   - 已进入 OpenClaw 执行
   - 登录失败
   - 页面风控
   - 上传失败
   - 提交失败
   - 已成功发布
2. 日志应能支持快速判断失败是系统问题还是平台问题

### 4. 保持兼容

1. 不破坏 fake/mock publisher 回退路径
2. 不破坏现有 `/publish` 与 `/openclaw/execute-publish` 承接能力
3. 不破坏前端当前已接好的发布记录字段

### 5. 后端验收输出

后端完成后需要回传：

1. commit hash
2. commit message
3. 改动文件列表
4. 真实发布接入说明
5. 成功结果或失败结果样例
6. 测试结果
7. `git status --short`

## 前端职责

### 1. 承接真实发布触发

1. `/review` 中“交给 OpenClaw 执行”要能驱动真实发布动作
2. 页面要明确显示当前是否处于真实账号验收模式
3. 不要让用户误以为当前仍是 fake 执行或演示态

### 2. 承接真实结果展示

以下页面要统一承接真实平台返回：

1. `/review`
2. `/dashboard`
3. `/posts/[id]`

至少要能展示：

1. 是否已交给 OpenClaw
2. 是否执行中
3. 是否已发布
4. 是否发布失败
5. 平台回写标识
6. 失败原因与失败分类
7. 下一步动作建议

### 3. 真实态与演示态分离

1. 接口成功时优先展示真实发布结果
2. 不允许真实验收模式下继续用演示文案覆盖真实结果
3. 如果当前没有真实返回，页面要明确显示“暂无真实平台回写”而不是伪造成功态

### 4. 前端验收输出

前端完成后需要回传：

1. commit hash
2. commit message
3. 改动文件列表
4. 真实结果承接策略说明
5. 页面影响范围说明
6. `npm run lint` 结果
7. `npm run build` 结果
8. `git status --short`

## 推荐执行步骤

### 步骤 1：准备验收样本

1. 选 1 条已 `approved` 内容
2. 确认该内容的标题、正文、素材完整
3. 确认该内容归属真实账号

### 步骤 2：触发真实发布

1. 从 `/review` 或等价真实入口触发“交给 OpenClaw 执行”
2. 后端进入 `publishing`
3. 观察是否进入真实平台执行

### 步骤 3：验证结果回写

1. 若成功：
   - 确认帖子状态进入 `published`
   - 确认存在平台成功标识或等价结果
2. 若失败：
   - 确认帖子状态进入 `publish_failed`
   - 确认失败原因和分类可解释

### 步骤 4：验证页面展示

1. `/dashboard` 是否展示真实当前状态
2. `/posts/[id]` 是否展示真实发布记录
3. `/review` 是否展示真实回写结果或下一步动作

## 建议优先验收的失败场景

如果成功路径暂时不稳定，优先接受以下失败路径作为通过样本：

1. 登录态失效
2. 上传失败
3. 页面提交失败
4. 平台限流

前提是：

1. 失败结果是真实触发的
2. 后端有真实分类
3. 前端页面正确展示

## 判定口径

### 通过

1. 拿到至少 1 次真实成功结果
2. 或拿到至少 1 次真实失败结果，并且页面承接正确

### 不通过

1. 只在系统内部切状态，没有真实平台执行痕迹
2. 只有日志，没有页面回写
3. 页面仍主要展示演示态，无法区分真实成功与真实失败

## 验收完成后下一步

如果本轮通过，下一步进入：

1. 真实数据回收
2. 指标历史快照承接
3. 多账号与失败重试策略细化
