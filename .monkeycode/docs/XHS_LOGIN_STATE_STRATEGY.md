# 小红书登录态接入与复用策略

## 文档目标

本文件用于明确：当小红书网页端只能通过扫码登录或手机号验证码登录时，系统应如何完成账号接入、登录态保存、后续复用、失效检测和续期处理，并将该能力与 OpenClaw、后端和网页端协同起来。

## 问题定义

当前小红书网页端不适合直接作为“后台账号密码登录”的第三方登录源。常见可用登录方式主要是：

1. 扫码登录
2. 手机号验证码登录

这意味着系统不能简单依赖“用户登录自己的后台”来自动获得小红书登录态，而需要设计一套“账号接入 + 登录态保存 + 后续复用”的机制。

## 一句话策略

系统不尝试绕过小红书原生登录方式，而是把扫码/验证码登录设计为一次账号接入动作；接入成功后保存登录态，后续发布和拉数都复用该登录态，失效后再引导用户重新接入。

## 核心原则

1. 不绕过扫码或验证码，而是接纳其为首次接入步骤。
2. 用户感知上尽量是一体化体验，但系统内部必须显式管理小红书登录态。
3. 登录态必须与具体小红书账号绑定，不能混用。
4. 发布链路与数据拉取链路必须复用同一份登录态。
5. 登录态失效后必须可检测、可提示、可重新接入。

## 总体流程

### 1. 首次接入

1. 用户在后台点击“连接小红书”或等价入口。
2. 系统为该账号分配一个受控浏览器会话。
3. OpenClaw 打开小红书创作者中心登录页。
4. 用户通过扫码或手机号验证码完成登录。
5. 登录成功后，系统验证当前会话已可进入创作者中心。
6. 系统保存该浏览器会话的登录态。
7. 后台将该账号标记为“已接入”。

### 2. 日常复用

1. 用户在后台或 OpenClaw 发起发布或拉数请求。
2. OpenClaw 先加载该账号保存的登录态。
3. 系统先做一次轻量有效性检查。
4. 若检查通过，直接执行发布或数据拉取。

### 3. 失效检测

1. 若访问创作者中心时被重定向到登录页，说明登录态已失效。
2. 若操作关键页面时出现明确未登录提示，也视为登录态失效。
3. 系统将该账号标记为 `reauth_required`。
4. 网页端和 OpenClaw 都提示用户重新接入。

### 4. 续期处理

1. 用户再次进入“连接小红书”或“重新登录小红书”流程。
2. 重新执行扫码或验证码登录。
3. 登录成功后覆盖旧登录态。
4. 恢复该账号的可发布、可拉数状态。

## 推荐接入方案

### 方案 A：OpenClaw 受控浏览器接入

这是当前最推荐方案。

#### 流程

1. OpenClaw 在服务器上启动 Chrome / Chromium。
2. OpenClaw 打开小红书创作者中心登录页。
3. 用户通过 VNC、远程桌面或等价方式看到登录页。
4. 用户手动扫码或输入验证码完成登录。
5. OpenClaw 保存当前浏览器登录态。

#### 优点

1. 与当前 OpenClaw 发布执行环境一致。
2. 登录态直接保存在实际执行发布和拉数的浏览器环境中。
3. 不需要额外设计复杂跨环境会话迁移。

#### 限制

1. 首次接入时需要人工参与。
2. 登录态失效时仍需重新扫码或验证码登录。

### 方案 B：网页登录接入后转移到执行环境

该方案只有在你未来明确需要“网页登录时就完成账号接入”时再考虑。

#### 流程

1. 用户在网页端点击连接小红书。
2. 系统引导到可控登录会话。
3. 登录完成后，将登录态同步到 OpenClaw 执行环境。

#### 限制

1. 会话迁移更复杂。
2. 容易出现“网页已登录、执行环境未登录”的不一致。

当前阶段不建议优先做。

## 登录态保存策略

### 保存内容

建议至少保存以下内容：

1. 浏览器 cookies
2. localStorage / sessionStorage 中与登录相关的状态
3. Playwright `storageState` 或等价会话快照
4. 对应账号标识与保存时间

### 保存单位

登录态应以“小红书账号”为单位保存，而不是以用户设备或单次任务为单位保存。

### 推荐字段

1. `accountId`
2. `accountName`
3. `connectionStatus`
4. `loginStatePath` 或等价存储引用
5. `connectedAt`
6. `lastValidatedAt`
7. `lastUsedAt`
8. `reauthRequired`
9. `lastAuthError`

## 登录态复用策略

### 发布前检查

每次发布前建议执行：

1. 加载保存的登录态
2. 打开创作者中心首页或发布页
3. 检查是否仍处于登录状态
4. 若有效，再继续发布动作

### 拉数前检查

每次拉取作品数据前建议执行：

1. 加载保存的登录态
2. 打开创作者中心作品管理页或等价页面
3. 检查是否仍能访问作品列表
4. 若有效，再继续拉数

### 复用原则

1. 发布和拉数共用同一份登录态。
2. 同一账号在短时间内避免创建多份冲突浏览器会话。
3. 若未来支持多账号，需做到一账号一登录态。

## 失效判定规则

以下任一情况出现时，应判定为登录态失效：

1. 页面跳转到登录页。
2. 页面出现要求扫码或验证码登录的提示。
3. 作品管理页无法访问且提示未登录。
4. 发布页无法访问且提示未登录。
5. 登录相关关键 cookies 丢失或明显失效。

## 失效后的系统行为

### 对后端

1. 将账号状态更新为 `reauth_required`。
2. 记录最近一次认证失败时间和错误摘要。
3. 阻止继续发起真实发布或真实拉数。

### 对前端

1. 在账号页显示“需要重新登录小红书”。
2. 在发布入口显示当前账号不可用。
3. 在数据页显示同步暂停原因。

### 对 OpenClaw

1. 主动通知用户当前账号登录态已失效。
2. 引导用户重新完成扫码或验证码登录。
3. 不应在明知失效时继续重复尝试提交发布。

## 续期策略

### 最小方案

1. 登录态失效后，人工重新扫码或验证码登录。
2. 登录成功后覆盖旧会话。
3. 恢复发布和拉数能力。

### 用户体验要求

1. 用户不需要理解 cookies、storageState 等技术细节。
2. 用户只需要知道“当前账号需要重新连接小红书”。
3. 续期入口应尽量集中，例如统一使用“重新连接小红书”。

## 前端产品表达建议

### 推荐文案

1. `连接小红书`
2. `已连接`
3. `连接已失效，请重新登录`
4. `重新连接小红书`
5. `最近一次验证成功于 ...`

### 不推荐文案

1. `绑定 cookies`
2. `导入 storageState`
3. `同步浏览器会话`

原因是这些属于实现细节，不适合暴露给普通用户。

## OpenClaw 产品表达建议

### 推荐消息模板

1. `小红书账号已连接，可以继续发布和查看数据。`
2. `当前小红书登录状态已失效，需要重新登录。`
3. `请完成扫码登录，登录成功后我会继续执行发布。`
4. `请完成验证码登录，成功后我会继续同步数据。`

## 安全与风控要求

1. 不在聊天消息、日志或前端页面明文暴露登录敏感信息。
2. 登录态文件应与账号绑定并限制访问范围。
3. 不跨账号复用同一份登录态。
4. 不依赖模拟绕过验证码或绕过扫码的手段作为正式方案。

## 当前阶段推荐落地方式

### 第一阶段

1. 单账号接入。
2. 使用 OpenClaw 受控浏览器。
3. 首次人工扫码登录。
4. 保存 Playwright `storageState`。
5. 发布前和拉数前都先校验登录态。
6. 失效后标记 `reauth_required` 并提醒用户重新连接。

### 第二阶段

1. 补齐网页登录入口与账号接入状态页。
2. 统一“后台登录 + 小红书接入”的用户体验。
3. 扩展到多账号时，保持一账号一会话。

## 验收口径

当以下条件同时成立时，可认为登录态策略落地成功：

1. 用户能通过扫码或验证码完成一次小红书接入。
2. 系统能保存并复用登录态。
3. 重开浏览器后仍能访问创作者中心而不跳登录。
4. 发布和拉数都使用同一份登录态。
5. 登录态失效时，系统能明确检测并提示重新连接。
