# 下一阶段执行分工

## 目标

把当前已完成的 `QQ -> OpenClaw -> backend -> /tasks -> /review -> /dashboard -> /posts/[id]` 前半段闭环，继续推进到“账号归属真实化、生成链路可承接、发布链路可调度、真实小红书最小验收”的可执行状态。

## 当前判断

1. 现在还不需要立即依赖真实小红书账号，仍可以先完成平台内部主链路。
2. 真正必须依赖真实小红书账号的节点，是“最小真实发布验收”和“真实数据回收验收”。
3. 下一阶段不要先去穷举小红书所有接口，而应先把内部适配层和状态流转做稳。

## 统一边界

1. 当前阶段不扩权限系统。
2. 当前阶段不做多账号自动调度策略，只做账号归属和手动选择可用。
3. 当前阶段不追求一次性找齐全部小红书网页接口。
4. 当前阶段所有页面和状态，优先围绕真实业务步骤组织，而不是围绕接口字段组织。

## 执行顺序

### 阶段 1：账号归属真实化

#### 后端

1. 为真实 QQ 入站生成的 `message task` 和对应 `post` 稳定回写 `accountId`、`accountName`。
2. 明确账号归属来源规则。
3. 保持 `GET /api/tasks`、`GET /api/posts`、`GET /api/posts/{id}` 的账号字段一致，不再出现 `post.accountId` 和 `task.accountId` 同时为空的主路径数据。
4. 补最小测试，覆盖：
   - QQ 真实任务创建后带账号归属
   - `task` 与 `post` 的账号归属一致
   - 老种子数据不被破坏

#### 前端

1. 去掉 `/review`、`/dashboard`、`/posts/[id]` 中基于种子账号的主路径展示依赖。
2. 保留最小兼容，但兼容只允许在接口失败时生效，不允许真实接口返回空归属时继续伪造账号展示。
3. 在页面上明确区分“真实账号归属已返回”和“当前未分配账号”两种状态。

#### 验收标准

1. `post_f01d2157a6` 这类真实 QQ 验收帖子，在详情页中看到的账号归属来自真实接口，而不是前端种子兜底。
2. `/tasks`、`/review`、`/dashboard`、`/posts/[id]` 对同一任务的账号展示一致。

#### 是否依赖真实小红书账号

不依赖。

### 阶段 2：打通真实生成链路

#### 后端

1. 把 `pending_generation` 之后的最小状态流转补齐，至少覆盖：
   - `pending_generation`
   - `copy_generated`
   - `images_generated`
   - `waiting_review`
   - `approved`
2. 为 `message task` 和 `post` 明确生成结果承接方式：
   - 文案候选如何进入 `post`
   - 图片候选如何进入 `assets` 或等价关联结构
3. 若当前生成仍为占位实现，也必须让状态推进、字段回写和重试语义真实可用。
4. 补最小测试，覆盖：
   - 从 `pending_generation` 推进到可确认状态
   - 重复触发不导致脏状态覆盖
   - 文案/图片生成缺一时页面可识别当前准备度

#### 前端

1. `/tasks` 页面改成真实展示“文案已生成 / 图片已生成 / 等待确认”的准备度，而不是继续把 `pending_generation` 一律显示成单一阶段。
2. `/review` 页面改成优先消费真实候选内容和真实素材，不再主要依赖展示层拼接的默认候选。
3. 在内容确认台明确展示“这次看到的是系统真实生成结果”还是“当前仍是空态占位”。

#### 验收标准

1. 任选一条真实 QQ 任务，可以从待生成推进到可确认。
2. `/tasks`、`/review`、`/posts/[id]` 中看到的文案、图片准备状态一致。

#### 是否依赖真实小红书账号

不依赖。

### 阶段 3：收口帖子页承接策略

#### 后端

1. 明确 `GET /api/posts` 对不同状态帖子是否都返回，保持排序和字段稳定。
2. 如果列表继续只看已发布内容，保持该策略稳定并在契约文档写清楚。
3. 如果列表需要同时承接待发送和待确认帖子，补充最小筛选参数或聚合字段，但不要破坏现有已发布视图。

#### 前端

1. 决定 `/posts` 是“已发布内容页”还是“帖子全生命周期页”，不要继续处于语义摇摆状态。
2. 如果仍只展示已发布内容：
   - 页面文案要明确这是“发布后复盘页”
   - 不再暗示所有真实帖子都会出现在这里
3. 如果改为全生命周期：
   - 明确分组展示 `待确认`、`待发送`、`已发布`
   - 保持多账号视角和后续建议文案一致

#### 验收标准

1. 用户能明确知道为什么某条真实 QQ 帖子会出现在 `/posts` 或不会出现在 `/posts`。
2. `/posts` 与 `/posts/[id]` 的叙事一致，不再让用户误以为列表漏数据。

#### 是否依赖真实小红书账号

不依赖。

### 阶段 4：设计并实现发布适配层

#### 后端

1. 抽象统一发布适配层，不直接在业务层写死小红书网页细节。
2. 最小接口建议覆盖：
   - `preparePublish`
   - `submitPublish`
   - `writebackPublishResult`
   - `fetchMetrics`
3. 明确发布任务与业务状态映射：
   - `approved -> publishing -> published`
   - `approved -> publishing -> publish_failed`
4. 明确失败分类最小语义：
   - 可重试失败
   - 不可重试失败
   - 平台限流
5. 在适配层下允许先接 mock / fake publisher，用于跑通内部闭环。

#### 前端

1. `/dashboard` 和 `/posts/[id]` 统一围绕适配层返回的结果展示，不直接猜测平台状态。
2. 在页面上把“已交给 OpenClaw”“平台处理中”“发布失败待处理”分清。
3. 为失败结果展示下一步动作建议，且建议文案来自真实失败分类，不由页面随意拼接。

#### 验收标准

1. 即使还没接真实小红书，系统内部也能把一条 `approved` 帖子推进到 `publishing`，再推进到 `published` 或 `publish_failed`。
2. `/dashboard` 和 `/posts/[id]` 能稳定展示这条发布链路。

#### 是否依赖真实小红书账号

不依赖。

### 阶段 5：OpenClaw 内部发布闭环

#### 后端

1. 把发布适配层接到真实的 OpenClaw 调度入口上。
2. 允许先用受控执行模式，不要求一开始就自动批量发布。
3. 确保执行日志、结果回写、失败重试入口都能稳定落库。

#### 前端

1. `/review` 中“交给 OpenClaw 执行”要能驱动真实状态变化，而不是只改前端展示。
2. `/dashboard` 中能看到某次执行的最新阶段和回写结果。
3. `/posts/[id]` 中能看到发送记录明细。

#### 验收标准

1. 从 `/review` 触发后，真实帖子能进入 `publishing`。
2. `/dashboard` 与 `/posts/[id]` 可以看到同一次执行记录。

#### 是否依赖真实小红书账号

不依赖，可以先跑 fake publisher。

### 阶段 6：真实小红书最小发布验收

#### 后端

1. 在不破坏适配层边界的前提下，接入真实小红书发布实现。
2. 先只验收单账号、单条图文、最小成功路径。
3. 记录登录失效、风控、限流、上传失败等最小异常分类。

#### 前端

1. 页面上不要假装“已经稳定支持真实小红书”，而是准确展示当前是否处于真实账号验收模式。
2. 在 `/dashboard` 和 `/posts/[id]` 中展示真实平台返回结果和失败原因。

#### 验收标准

1. 至少 1 条内容通过真实小红书账号完成最小发布验收。
2. 至少拿到 1 次真实成功结果或 1 次可解释失败结果。

#### 是否依赖真实小红书账号

依赖。

### 阶段 7：真实数据回收

#### 后端

1. 基于适配层补齐真实帖子数据抓取。
2. 最小覆盖：
   - 浏览
   - 点赞
   - 收藏
   - 评论
3. 明确抓取频率、失败重试和历史快照写入策略。

#### 前端

1. `/posts`、`/posts/[id]`、`/dashboard` 统一消费真实回收数据。
2. 页面上区分“真实平台数据”“暂无回收结果”“历史快照为空”三种状态。

#### 验收标准

1. 至少 1 条真实发布内容在详情页看到真实历史快照。
2. 列表、详情、发布中心对同一条内容的数据口径一致。

#### 是否依赖真实小红书账号

依赖。

## 当前建议的立即执行项

1. 后端先做阶段 1：补齐真实 QQ 帖子的 `accountId`、`accountName` 回写。
2. 前端同步收口详情页和确认台的账号兜底逻辑，避免继续展示错误归属。
3. 后端随后进入阶段 2：补齐 `pending_generation` 之后的真实生成状态推进。
4. 前端同步把 `/tasks` 和 `/review` 切到真实生成结果承接。
