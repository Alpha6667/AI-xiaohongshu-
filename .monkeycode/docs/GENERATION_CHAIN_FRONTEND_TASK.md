# 前端任务单：真实生成链路承接

## 目标

把前端从“只知道任务已入站”推进到“能真实展示文案已生成、图片已生成、等待确认”的状态，让 `/tasks`、`/review`、`/posts/[id]` 看到的是后端真实生成结果，而不是长期依赖展示层默认占位。

## 当前问题

1. 账号归属真实化已经完成，但真实任务大多仍停留在 `pending_generation` 展示。
2. `/tasks` 目前还不能稳定表达真实准备度变化。
3. `/review` 仍可能主要依赖默认候选文案、默认图片或空态叙事。
4. `/posts/[id]` 还不能明确区分“这条内容已经真实生成”还是“目前还只是空壳帖子”。

## 本轮边界

1. 本轮只做生成链路承接，不扩真实小红书发布。
2. 本轮不要求前端自己伪造生成结果。
3. 本轮允许保留接口失败时的整页 fallback，但不允许在接口成功时继续长期用默认候选掩盖真实空态。

## 必须交付

### 1. 收口 `/tasks` 页面准备度展示

1. `/tasks` 不再把真实任务一律展示为单一“待生成”。
2. 需要根据后端真实字段展示至少这些信息：
   - 文案是否已生成
   - 图片是否已生成
   - 是否已进入人工确认
   - 下一步动作是什么
3. 页面文案要让用户一眼看懂：当前是“还在生成”“文案已好缺图片”“可去确认台处理”。

### 2. 收口 `/review` 页面候选内容来源

1. `/review` 优先消费后端真实返回的标题、正文、标签和素材。
2. 如果后端真实返回已有候选结果，页面不再优先展示展示层拼接的默认候选版本。
3. 如果后端真实返回仍未生成完成，要明确展示生成未完成空态，而不是让用户误以为这些候选已经真实存在。

### 3. 收口 `/posts/[id]` 页面生成状态叙事

1. 详情页要能明确看出当前帖子是否已经进入“可确认内容”阶段。
2. 如果文案已生成但图片未生成，要明确显示部分准备完成，而不是笼统显示“待生成”。
3. 如果文案和图片都已就绪，页面文案要与 `/tasks`、`/review` 保持一致。

### 4. 收口展示层工具

重点检查并调整：

1. `frontend/src/lib/product.ts`
2. `adaptMessageTasks`
3. `buildMessageTasks`
4. 与候选文案、候选素材、准备状态相关的辅助函数

要求：

1. 接口成功时优先使用真实生成结果。
2. 默认候选只允许作为接口失败时的整页回退或明确标注的演示态。
3. 不允许“后端还没生成，前端却看起来像已经生成完了”的主路径误导。

### 5. 页面文案同步

1. 对以下几种状态给出一致中文表达：
   - 还在生成文案和图片
   - 文案已生成，等待图片
   - 图片已生成，等待文案
   - 已可进入确认台
2. `/tasks`、`/review`、`/posts/[id]` 对这些状态的表达必须一致。

### 6. 验证

必须执行：

1. `cd frontend && npm run lint`
2. `cd frontend && npm run build`

## 建议改动点

1. `frontend/src/lib/product.ts`
2. `frontend/src/app/tasks/page.tsx`
3. `frontend/src/app/review/page.tsx`
4. `frontend/src/app/posts/[id]/page.tsx`
5. 如有必要，补充 `frontend/src/lib/api/types.ts`

## 验收标准

1. 任选一条真实 QQ 任务，当后端状态推进后，`/tasks` 能显示真实准备度变化。
2. `/review` 优先展示后端真实生成结果，而不是默认候选。
3. `/posts/[id]` 能区分“尚未生成完成”和“已可确认”。
4. 三个页面对同一条任务的生成阶段表达一致。
5. `npm run lint` 通过。
6. `npm run build` 通过。
