# 小红书项目最后收尾事项清单

## 当前判断

项目已经完成一次可确认的真实小红书发布成功，说明主链路已经从“概念验证”推进到“真实业务动作验证”。

当前剩余工作不再是重做主架构，而是围绕稳定性、可复用性和发布后闭环做最后收尾。

## P0 必做项

### 1. 固化真实发布脚本

把这次跑通的小红书新版发布页流程固化到 OpenClaw 发布脚本里，避免下次再依赖临场修 selector。

应固定的顺序是：

1. 打开发布页
2. 先上传图片
3. 等页面切到图文编辑模式
4. 定位标题框 `placeholder="填写标题会有更多赞哦"`
5. 填写正文 `contenteditable`
6. 点击发布按钮

### 2. 固化登录态续期流程

需要把“登录态失效 -> 重新登录 -> 继续发布”的流程做成稳定规则。

必须明确：

1. 登录必须发生在真实发布使用的同一个浏览器 profile 中
2. 登录失效时要能明确返回 `reauth_required` 一类结果
3. 不要再等到点击发布时才被 `redirectReason=401` 打回登录页

### 3. 发布前增加防重复检查

在真实发布前，必须先校验目标 `postId` 当前状态。

规则：

1. 如果已是 `published`，直接阻止再次发布
2. 避免重复发布已成功内容
3. 本次已经验证：`post_877f43cbed` 属于已发布对象，不应再重复发送

### 4. 稳定 OpenClaw 主服务操作边界

后续排障时，不要再通过重启现网 OpenClaw 主服务做验证。

必须区分：

1. 现网主服务
2. 独立测试实例
3. 临时前台验证进程

## P1 应做项

### 1. 验证发布后状态查询闭环

需要确认 QQ / OpenClaw 的“查状态”链路已经完全围绕真实 `post` 工作：

1. 查询状态时不再新建 task/post
2. 正确读取 `GET /api/posts/{post_id}`
3. 能返回真实发布状态

### 2. 验证前端详情展示闭环

前端需要最终确认以下内容和 backend 返回一致：

1. `published`
2. `platformPostId`
3. 发布记录
4. 真实素材/截图信息

### 3. 回收真实作品数据

需要继续完成发布后的真实数据回收和展示，包括：

1. 标题
2. 发布时间
3. 点赞数
4. 收藏数
5. 评论数
6. 审核/发布状态

并把这些数据：

1. 回写 backend
2. 前端展示出来

### 4. 清理 qqbot/runtime 脏问题

之前已经出现过：

1. `ENOTEMPTY`
2. plugin runtime deps 脏目录

虽然这次不一定直接阻塞真实发布，但会影响后续稳定性，应该收口。

## P2 优化项

### 1. QQ 端提醒模板

补齐统一提醒模板：

1. 生成完成
2. 待确认
3. 发布中
4. 已发布
5. 登录失效
6. 发布失败

### 2. 新版发布页适配文档化

把新版页面的关键 selector、页面切换条件和失败信号整理成独立文档，便于以后直接复用。

### 3. 模型与执行链解耦

后续应把：

1. 模型切换排障
2. OpenClaw/Gateway 排障
3. 小红书业务执行

分成独立问题处理，避免再因为模型问题整体阻塞业务主线。

## 当前最值得优先做的三件事

### 第一优先级

把这次真实成功发布流程固化进 OpenClaw 发布脚本。

### 第二优先级

加上发布前防重复检查，阻止已发布 `post` 被再次发送。

### 第三优先级

做一轮发布后数据回收验证，确认从发布成功到数据回流的闭环成立。

## 结论

项目已经不再缺“能不能发”的主能力，而是缺“稳定复用、避免误发、发布后可追踪”的最后一层产品和工程收口。

因此当前阶段最合理的目标不是继续扩范围，而是把真实发布成功经验沉淀成可重复执行的标准流程。
