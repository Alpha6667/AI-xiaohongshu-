# OpenClaw 到小红书产品主链路

## 文档目标

本文件用于统一前端、后端与 OpenClaw 对产品主流程的理解，明确“消息入口 + 网页管理后台 + 小红书发布执行”三者之间的关系，避免后续实现偏离用户真实使用方式。

## 一句话定义

用户先在 QQ 中向 OpenClaw 下达内容需求，后台生成同一份文案与图片，OpenClaw 和网页端同时展示同一份候选内容，用户可在任一端确认发布，随后由 OpenClaw 执行小红书发布，并将审核与发布结果同时回传到 QQ 和网页端。

## 核心原则

1. OpenClaw 是消息入口、提醒入口和发布执行入口。
2. HTML 网页是可视化工作台、人工确认入口和结果查看入口。
3. QQ/OpenClaw 与网页端展示的是同一份任务、同一份文案、同一组图片、同一个发布结果。
4. 用户可以在 OpenClaw 或网页端完成确认动作，但两边操作的都是同一个内容对象。
5. 发布结果、审核状态和失败原因必须双端同步，不允许一端成功、一端仍停留旧状态。

## 目标用户体验

1. 用户先通过 QQ 和 OpenClaw 对话，不必先打开后台页面。
2. 用户发一句自然语言需求，例如“我要出一个关于乌鸦喝水的故事”。
3. 系统生成候选文案和候选图片后，用户既能在 QQ 里看到，也能在网页端看到。
4. 用户确认后，可以直接在 QQ 里说“就发这个”，也可以在网页端点击发布。
5. 发布进入小红书审核流程后，用户能同时在 QQ 和网页端收到进度变化。

## 主流程

### 1. 需求发起

1. 用户在 QQ 中向 OpenClaw 发送内容需求。
2. OpenClaw 将消息转发给后台。
3. 后台创建一条 `message task`，并为该任务关联或创建 `post`。

### 2. 内容生成

1. 后台根据消息任务生成候选文案。
2. 后台根据消息任务生成候选图片。
3. 后台将生成结果保存为统一内容对象，供 OpenClaw 和网页端共同消费。

### 3. 双端展示

1. OpenClaw 在 QQ 中把候选文案和候选图片发给用户。
2. 网页端在任务页、确认页或帖子页展示同一份候选文案和候选图片。
3. 双端展示的内容版本必须一致，避免 QQ 中看到一版、网页中看到另一版。

### 4. 人工确认

1. 用户可在 QQ/OpenClaw 中选择当前候选内容并下达“发这个”的指令。
2. 用户也可在网页端修改、保存、提交确认或直接触发发布。
3. 任一入口完成确认后，后台都应更新同一条 `post` 和同一条任务链路状态。

### 5. 发布执行

1. 后台将最终确认的文案和图片交给 OpenClaw。
2. OpenClaw 调用浏览器执行环境或发布执行器，将内容上传到小红书。
3. OpenClaw 执行结果通过同步响应和异步回写返回后台。

### 6. 平台审核与发布

1. 内容提交到小红书后，先进入平台审核过程。
2. 审核通过后，帖子进入已发布状态。
3. 审核未通过或执行失败时，系统需保留可解释原因和执行日志。

### 7. 结果回收与通知

1. 网页端更新帖子状态、发布记录、失败原因和平台帖子标识。
2. OpenClaw 在 QQ 中主动提醒用户审核进展、发布成功或发布失败。
3. 双端都应能查看最终结果，不应只有一端可见。

## 推荐状态链路

为避免前后端、OpenClaw 对状态理解不一致，建议统一使用如下状态语义：

1. `message_received`：收到 OpenClaw 转发的原始需求消息。
2. `pending_generation`：等待生成文案与图片。
3. `copy_generated`：文案已生成。
4. `images_generated`：图片已生成。
5. `waiting_selection`：候选内容已齐备，等待用户确认。
6. `approved`：用户已确认可发布内容。
7. `publishing`：OpenClaw 正在执行发布提交。
8. `under_review`：内容已提交到小红书，等待平台审核。
9. `published`：小红书审核通过并已发布。
10. `rejected`：小红书审核未通过。
11. `publish_failed`：执行阶段失败，尚未成功提交到平台。

## 双端一致性要求

1. QQ/OpenClaw 与网页端必须引用同一 `postId` 和同一组素材标识。
2. 任一端的确认动作都必须写回统一后端对象，而不是各自维护副本。
3. 任一端看到的状态文案应源自同一状态机，不应出现一端显示“已发布”、另一端显示“待确认”。
4. 如果用户在网页端修改确认版文案，OpenClaw 后续发送给用户的内容也应是修改后的版本。
5. 如果用户在 QQ 中选择了某一版候选图，网页端也应立即反映该选择结果。

## 通知要求

### OpenClaw / QQ 通知

1. 生成完成时通知用户查看候选文案和图片。
2. 发布开始时通知用户“已进入发布流程”。
3. 提交小红书成功时通知用户“已提交，等待审核”。
4. 审核通过时通知用户“已发布”。
5. 审核未通过或执行失败时通知用户原因摘要。

### 网页端通知

1. 在任务页、确认页、发布中心和帖子详情页展示状态变化。
2. 展示执行日志摘要、失败原因和平台帖子标识。
3. 支持用户回看历史审核记录和发布记录。

## 当前范围边界

1. 当前先验证单账号、单条内容、单次真实发布闭环。
2. 当前不扩多账号调度。
3. 当前不扩批量发布。
4. 当前不扩复杂重试系统。
5. 当前不扩权限系统。

## 对实现方的直接要求

### 对 OpenClaw

1. 负责承接 QQ 消息入口。
2. 负责把消息可靠转发给后台。
3. 负责把后台生成结果回发到 QQ。
4. 负责承接“发这个”的确认指令。
5. 负责执行小红书发布，并把执行结果回写后台。

### 对后端

1. 负责维护统一任务对象和统一帖子对象。
2. 负责生成文案与图片，并保存统一结果。
3. 负责把同一份内容提供给网页端和 OpenClaw。
4. 负责承接 OpenClaw 的发布回写、审核状态和失败信息。

### 对前端

1. 负责把同一条任务链路可视化展示出来。
2. 负责展示候选文案、候选图片、确认版内容和发布结果。
3. 负责允许用户在网页端完成与 OpenClaw 等价的确认操作。
4. 负责让用户清楚看到“当前做到哪一步、下一步该做什么、失败在哪里”。

## 验收口径

当以下条件同时成立时，可认为这条产品主链路成立：

1. 用户在 QQ 中发送需求后，后台能创建真实任务。
2. 候选文案和候选图片能同时在 OpenClaw 和网页端看到。
3. 用户在任一端确认后，另一端能看到同一确认结果。
4. OpenClaw 能按确认结果真实触发小红书发布。
5. 小红书审核中、审核通过、审核失败或执行失败结果能双端同步。
